Module 01
{{ ref() }} vs {{ source() }}
The two most fundamental Jinja functions. ref() is for models you own. source() is for tables loaded externally. Both compile to fully qualified Snowflake object names.
{{ ref('model_name') }} — Cross-model Reference
JINJASNOWFLAKE SQLWHY
✦ DBT Model (Jinja)
-- models/marts/fct_claims.sql
SELECT
    c.claim_id,
    c.patient_id,
    p.payer_name,
    c.billed_amount
FROM {{ ref('stg_claims') }}  -- dbt resolves this
AS c
JOIN {{ ref('dim_payers') }} AS p
  ON c.payer_id = p.payer_id
dbt compile → fully qualified Snowflake SQL
✦ Compiled Snowflake SQL
SELECT
    c.claim_id, c.patient_id, p.payer_name, c.billed_amount
FROM ANALYTICS_DB.STAGING.STG_CLAIMS  -- fully qualified
AS c
JOIN ANALYTICS_DB.MARTS.DIM_PAYERS AS p
  ON c.payer_id = p.payer_id
🧠
Why ref() instead of hardcoding?
1. DAG engine: Every ref() adds an edge to the dependency graph — dbt knows fct_claims depends on stg_claims and executes them in order.
2. Environment portability: In DEV the table lives in DEV_DB.STAGING, in PROD it's ANALYTICS_DB.STAGING. ref() auto-resolves to the right database for the active target — one model file works everywhere.
3. Lineage & docs: dbt Explorer traces every column back to its source because ref() creates explicit graph edges.
❄️
Snowflake-specific: The compiled output is always DATABASE.SCHEMA.TABLE — the three-part identifier Snowflake requires for cross-schema joins. dbt injects the correct database from your profiles.yml target.
{{ source('src', 'table') }} — Raw / External Tables
JINJASNOWFLAKE SQLWHY NOT ref()
✦ DBT Model (Jinja)
SELECT
    claim_id,
    UPPER(claim_status) AS claim_status,
    billed_amount
FROM {{ source('credible', 'claims') }}
WHERE load_date = CURRENT_DATE()
✦ sources.yml (declares the source)
sources:
  - name: credible
    database: RAW_DB
    schema: CREDIBLE_ALPHA
    freshness:
      warn_after:  {count: 6,  period: hour}
      error_after: {count: 24, period: hour}
    tables:
      - name: claims
        loaded_at_field: load_date
        description: "Raw claims from Credible Alpha EHR"
compile
✦ Compiled Snowflake SQL
SELECT
    claim_id,
    UPPER(claim_status) AS claim_status,
    billed_amount
FROM RAW_DB.CREDIBLE_ALPHA.CLAIMS
WHERE load_date = CURRENT_DATE()
🧠
ref() vs source() — the contract:
ref() = tables dbt built. source() = tables ADF/Fivetran/Snowpipe loaded. This boundary enables source freshness checks (dbt source freshness) — dbt can alert you when RAW data stops arriving. You can't do freshness checks with ref() because dbt controls when its own models run.

{% macro %} — Reusable Jinja Functions
Macros are Jinja functions that generate SQL at compile time. Think of them as stored procedures that run before Snowflake ever sees the query.
Basic Macro — cents_to_dollars()

✦ macros/cents_to_dollars.sql
{% macro cents_to_dollars(column_name, scale=2) %}
    ROUND({{ column_name }} / 100.0, {{ scale }})
{% endmacro %}
✦ Usage in model
SELECT
    claim_id,
    {{ cents_to_dollars('billed_cents') }}        AS billed_amount,
    {{ cents_to_dollars('paid_cents', scale=4) }}  AS paid_amount
FROM {{ ref('stg_claims') }}
compile
✦ Compiled Snowflake SQL
SELECT
    claim_id,
    ROUND(billed_cents / 100.0, 2) AS billed_amount,
    ROUND(paid_cents   / 100.0, 4) AS paid_amount
FROM ANALYTICS_DB.STAGING.STG_CLAIMS
generate_schema_name() Override — Enterprise Pattern
OVERRIDE MACROCRITICAL
✦ macros/generate_schema_name.sql
{% macro generate_schema_name(custom_schema_name, node) %}
    {% set default_schema = target.schema %}
    {% if custom_schema_name is none %}
        {{ default_schema }}
    {% else %}
        {{ custom_schema_name | trim }}  -- exact name, no env prefix
    {% endif %}
{% endmacro %}
🧠
Why override this? By default dbt prefixes schemas with the target name: config(schema='marts') in prod becomes PROD_MARTS. This override makes dbt use the exact name. Power BI connections to MARTS won't break across environments — critical for enterprise Snowflake.

  {% set payer_ids = results.columns[0].values() %}
{% else %}

{% for %} Loop — AR Aging Bucket Pivot
JINJA LOOP
✦ DBT Model
{% set buckets = [
    ('0_30',    0,   30),
    ('31_60',  31,   60),
    ('61_90',  61,   90),
    ('91_plus',91, 9999)
] %}

SELECT
    facility_id,
{% for label, lo, hi in buckets %}
    SUM(CASE WHEN days_out BETWEEN {{lo}} AND {{hi}} THEN billed_amount ELSE 0 END)
        AS ar_{{label}}{% if not loop.last %},{% endif %}
{% endfor %}
FROM {{ ref('fct_claims') }} GROUP BY 1
compile
✦ Compiled
SELECT facility_id,
    SUM(CASE WHEN days_out BETWEEN 0  AND 30   THEN billed_amount ELSE 0 END) AS ar_0_30,
    SUM(CASE WHEN days_out BETWEEN 31 AND 60   THEN billed_amount ELSE 0 END) AS ar_31_60,
    SUM(CASE WHEN days_out BETWEEN 61 AND 90   THEN billed_amount ELSE 0 END) AS ar_61_90,
    SUM(CASE WHEN days_out BETWEEN 91 AND 9999 THEN billed_amount ELSE 0 END) AS ar_91_plus
FROM ANALYTICS_DB.MARTS.FCT_CLAIMS GROUP BY 1
💡
loop.last trick: {% if not loop.last %},{% endif %} prevents trailing commas — the most common Jinja-in-SQL bug. Also available: loop.first, loop.index (1-based), loop.index0 (0-based), loop.length.

Module 06
Incremental Models — is_incremental() + {{ this }}
The most critical materialization for production Snowflake pipelines. Only processes new/changed rows. Full-refresh on first run, MERGE/INSERT on subsequent runs.
Incremental — MERGE strategy (upsert)
JINJAMERGE INTO
✦ DBT Model
{{ config(
    materialized         = 'incremental',
    unique_key           = 'claim_id',
    incremental_strategy = 'merge',
    cluster_by           = ['claim_date'],
    on_schema_change     = 'append_new_columns'
) }}

SELECT
    claim_id, patient_id, payer_id,
    billed_amount, claim_status, updated_at
FROM {{ source('credible', 'claims') }}

{% if is_incremental() %}
WHERE updated_at > (
    SELECT MAX(updated_at) FROM {{ this }}   -- {{ this }} = self-reference
)
{% endif %}
✦ First Run → CREATE TABLE
CREATE OR REPLACE TRANSIENT TABLE
    ANALYTICS_DB.MARTS.FCT_CLAIMS
AS (
  SELECT claim_id, ...
  FROM RAW_DB.CREDIBLE_ALPHA.CLAIMS
  -- no WHERE clause (is_incremental=false)
)
✦ Subsequent → MERGE INTO
MERGE INTO ANALYTICS_DB.MARTS.FCT_CLAIMS
USING (
  SELECT ...
  FROM RAW_DB.CREDIBLE_ALPHA.CLAIMS
  WHERE updated_at > (
    SELECT MAX(updated_at)
    FROM ANALYTICS_DB.MARTS.FCT_CLAIMS
  )
) AS src
ON dest.claim_id = src.claim_id
WHEN MATCHED THEN UPDATE SET ...
WHEN NOT MATCHED THEN INSERT ...
🧠
{{ this }} resolves to the current model's fully qualified Snowflake name. In the WHERE clause it means "give me rows newer than the latest row already in myself." Self-referential, environment-aware, and works across dev/prod automatically.

PAYER_NAME         VARCHAR
CONTRACT_RATE      NUMBER
DBT_SCD_ID        VARCHAR        -- hash of row (auto)
DBT_UPDATED_AT    TIMESTAMP_NTZ  -- last seen timestamp
DBT_VALID_FROM    TIMESTAMP_NTZ  -- when this version became active
DBT_VALID_TO      TIMESTAMP_NTZ  -- NULL=current, timestamp=expired

-- Current records:
SELECT * FROM ANALYTICS_DB.SNAPSHOTS.SNP_DIM_PAYERS
WHERE DBT_VALID_TO IS NULL;

-- Point-in-time (as of 2024-06-01):
SELECT * FROM ANALYTICS_DB.SNAPSHOTS.SNP_DIM_PAYERS
WHERE DBT_VALID_FROM <= '2024-06-01'
  AND (DBT_VALID_TO > '2024-06-01' OR DBT_VALID_TO IS NULL);
❄️
invalidate_hard_deletes=true: When a payer row disappears from source, dbt closes it by setting dbt_valid_to. Without this, deleted payers stay forever as "current." Essential for healthcare payer/facility dims where contracts expire.

🧠
Dynamic Table vs Incremental — when to choose which?
Dynamic Table: Snowflake manages the refresh schedule automatically. No dbt run needed after initial deployment — the table self-refreshes. Use when you need near-real-time data (minutes lag) without building a streaming pipeline. Snowflake handles the incremental logic internally.
Incremental model: You control refresh via dbt run cadence (triggered by ADF/Airflow/dbt Cloud). Use when you need custom merge logic, complex transformations, or audit hooks around the refresh.
❄️
target_lag values: '1 minute', '5 minutes', '1 hour', 'DOWNSTREAM' (refresh when a downstream DT needs it — most cost-efficient). refresh_mode='AUTO' lets Snowflake decide between incremental and full refresh based on the query. Use FULL to force always-full, INCREMENTAL to force incremental (errors if not supported).
⚡
on_configuration_change: Controls what dbt does if the Dynamic Table DDL has changed. apply = recreate it (downtime). continue = log warning, keep old version. fail = block the run. Use fail in CI to catch accidental DT definition changes.

Module 09 — NEW
Python Models (Snowpark) dbt 1.3+
Python models run on Snowpark — Snowflake's Python execution engine. Use them for ML feature engineering, complex transformations impossible in SQL, or pandas/sklearn integration.
Python Model — ML Feature Engineering on Snowpark
PYTHONSNOWPARK
✦ models/ml/features_claims_risk.py
# Python models use a standard model(dbt, session) signature
import pandas as pd

def model(dbt, session):

    # Configure — same keys as config() in SQL models
    dbt.config(
        materialized    = "table",
        packages        = ["pandas", "scikit-learn"],
        snowflake_warehouse = "ML_WH"
    )

    # ref() works identically — returns a Snowpark DataFrame
    claims_df  = dbt.ref("fct_claims")
    payers_df  = dbt.ref("dim_payers")

    # Convert to pandas for sklearn feature engineering
    claims_pd  = claims_df.to_pandas()
    payers_pd  = payers_df.to_pandas()

    merged = claims_pd.merge(payers_pd, on="payer_id")

    # Feature engineering
    merged["days_since_service"] = (
        pd.Timestamp.now() - pd.to_datetime(merged["service_date"])
    ).dt.days

    merged["denial_risk_flag"] = (
        (merged["days_outstanding"] > 90) &
        (merged["payer_tier"] == "COMMERCIAL")
    ).astype(int)

    # Return: Snowpark DF or pandas DF (both accepted)
    return merged[[
        "claim_id", "days_since_service",
        "denial_risk_flag", "payer_tier"
    ]]
✦ What Snowflake executes
-- dbt creates a stored procedure and calls it:
CREATE OR REPLACE PROCEDURE
    ANALYTICS_DB.ML.DBT_PYTHON_FEATURES_CLAIMS_RISK()
RETURNS TABLE()
LANGUAGE PYTHON
RUNTIME_VERSION = '3.9'
PACKAGES = ('snowflake-snowpark-python', 'pandas', 'scikit-learn')
HANDLER = 'compute'
AS '...(your python code)...';

-- Then materializes into a table:
CREATE OR REPLACE TABLE
    ANALYTICS_DB.ML.FEATURES_CLAIMS_RISK
AS CALL DBT_PYTHON_FEATURES_CLAIMS_RISK();
🧠
When to use Python models over SQL models: (1) ML feature engineering requiring pandas/sklearn transforms. (2) Complex string parsing (regex, NLP) not possible in SQL. (3) External API calls at transformation time. (4) Statistical operations (z-scores, rolling windows beyond SQL's OVER). For everything else, SQL is faster and cheaper on Snowflake.
❄️
Snowpark constraints: Python model runs in Snowflake's Python sandbox — no internet access, no file system writes. Packages must be on Snowflake's Anaconda channel or uploaded as stages. Always specify snowflake_warehouse — Python models need a warehouse (unlike some SQL views).
Module 10 — NEW
Contracts, Column Constraints & Grants dbt 1.5+
Model contracts enforce data types and column existence. Grants declaratively manage Snowflake RBAC. Together they replace fragile post_hook GRANT statements.
Model Contracts — Enforced Schema
CONTRACTDDL CONSTRAINTS
✦ models/schema.yml (contract definition)
models:
  - name: fct_claims
    config:
      contract:
        enforced: true       # dbt validates columns at compile time
    columns:
      - name: claim_id
        data_type: varchar
        constraints:
          - type: not_null
          - type: unique
        description: "Primary key — unique claim identifier"
      - name: billed_amount
        data_type: number
        constraints:
          - type: not_null
        description: "Total billed amount in USD"
      - name: payer_id
        data_type: varchar
        constraints:
          - type: not_null
          - type: foreign_key
            to: ref('dim_payers')
            to_columns: [payer_id]
      - name: claim_date
        data_type: date
        constraints:
          - type: not_null
✦ Snowflake DDL with constraints
CREATE OR REPLACE TABLE ANALYTICS_DB.MARTS.FCT_CLAIMS (
    claim_id       VARCHAR NOT NULL,
    billed_amount  NUMBER  NOT NULL,
    payer_id       VARCHAR NOT NULL,
    claim_date     DATE    NOT NULL
)
AS ( <your SELECT> );
🧠
Why contracts? Without a contract, dbt will run even if your SELECT accidentally drops a column or changes a data type — downstream consumers break silently. With enforced: true, dbt compares your SELECT output to the declared schema at compile time and fails before anything touches Snowflake. This is the dbt equivalent of a strongly-typed interface.

✦ macros/apply_masking_policies.sql (post_hook pattern)
{% macro apply_masking_policy(model, column, policy) %}
    ALTER TABLE {{ model }}
    MODIFY COLUMN {{ column }}
    SET MASKING POLICY {{ policy }};
{% endmacro %}
✦ The Snowflake masking policy itself
CREATE OR REPLACE MASKING POLICY
    ANALYTICS_DB.GOVERNANCE.PII_MASK_SSN
AS (val VARCHAR) RETURNS VARCHAR ->
CASE
    WHEN CURRENT_ROLE() IN ('CLINICAL_ADMIN', 'PHI_ROLE')
        THEN val             -- full SSN for authorized roles
    ELSE SHA2(val)          -- hashed for everyone else
END;
✦ Row Access Policy
CREATE OR REPLACE ROW ACCESS POLICY
    ANALYTICS_DB.GOVERNANCE.FACILITY_ROW_POLICY
AS (facility_id VARCHAR) RETURNS BOOLEAN ->
    facility_id IN (
        SELECT facility_id
        FROM ANALYTICS_DB.GOVERNANCE.USER_FACILITY_MAP
        WHERE username = CURRENT_USER()
    );

-- Apply to table:
ALTER TABLE ANALYTICS_DB.MARTS.FCT_CLAIMS
    ADD ROW ACCESS POLICY
    ANALYTICS_DB.GOVERNANCE.FACILITY_ROW_POLICY
    ON (facility_id);
❄️
HIPAA-compliant pattern: In behavioral health / RCM environments, Row Access Policies let you keep one physical fact table but serve facility-scoped views to each tenant automatically. A collector at Facility A never sees Facility B's AR data, enforced at the Snowflake engine level — even if Power BI doesn't filter correctly.

MetricFlow — Semantic Layer dbt 1.6+
MetricFlow is dbt's semantic layer. Define metrics once in YAML, query them consistently across any BI tool. Compiles to Snowflake SQL automatically.
MetricFlow — Semantic Model + Metric Definition
METRICFLOWGENERATED SQL
✦ models/semantics/sem_claims.yml
semantic_models:
  - name: sem_claims
    model: ref('fct_claims')
    description: "Semantic model for claims metrics"

    defaults:
      agg_time_dimension: claim_date

    dimensions:
      - name: claim_date
        type: time
        type_params:
          time_granularity: day
      - name: payer_id
        type: categorical
      - name: facility_id
        type: categorical
      - name: claim_status
        type: categorical

    measures:
      - name: total_billed
        description: "Total billed amount"
        agg: sum
        expr: billed_amount
      - name: claim_count
        description: "Number of claims"
        agg: count_distinct
        expr: claim_id
      - name: avg_days_outstanding
        agg: average
        expr: days_outstanding

metrics:
  - name: total_ar_value
    description: "Total accounts receivable billed amount"
    type: simple
    type_params:
      measure: total_billed

  - name: denial_rate
    description: "% of claims denied"
    type: ratio
    type_params:
      numerator:
        name: claim_count
        filter: "{{ Dimension('sem_claims__claim_status') }} = 'DENIED'"
      denominator:
        name: claim_count
✦ CLI query using MetricFlow
mf query \
  --metrics total_ar_value,denial_rate \
  --group-by payer_id,metric_time__month \
  --where "metric_time__month >= '2024-01-01'" \
  --limit 100
MetricFlow compiles → Snowflake SQL
✦ Generated Snowflake SQL
SELECT
    DATE_TRUNC('MONTH', claim_date)     AS metric_time__month,
    payer_id,
    SUM(billed_amount)               AS total_ar_value,
    COUNT_DISTINCT(CASE WHEN claim_status = 'DENIED'
        THEN claim_id END)
      / NULLIF(COUNT_DISTINCT(claim_id), 0) AS denial_rate
FROM ANALYTICS_DB.MARTS.FCT_CLAIMS
WHERE DATE_TRUNC('MONTH', claim_date) >= '2024-01-01'
GROUP BY 1, 2
LIMIT 100
🧠
Why MetricFlow? Without a semantic layer, every BI developer writes their own version of "total AR" with slightly different filters. One analyst uses billed_amount, another uses allowed_amount. The metrics diverge. MetricFlow makes "total_ar_value" a single source of truth — defined once in YAML, consistent across Power BI, Tableau, and direct Snowflake queries.
